## 3. Benchmarks

Method: `scripts/bench.zig`. For each group: 3 warm-up rounds, then 10 timed
rounds of `spawn` → `wait` around the whole child process, stdout → `/dev/null`.
**Warm-up and timed runs are interleaved across groups in rotating order**, so
load drift and cache pressure are shared by every group instead of penalising
whichever runs last. Throughput is normalised by **total corpus bytes on disk**
(654,899,262 / 131,128,199), which is a deliberately generous denominator: it
includes binary files that are skipped after the 8 KB NUL probe.

A first, *sequential* (non-interleaved) pass was also recorded
(`evidence/bench/*.txt` without the `_il` suffix). It reproduces the same
ordering with 10–15 % higher absolute times under higher load — kept as an
independent consistency check.

### Negative results (preserved on purpose)

* `zgrep` is **not** faster than ripgrep in general — it loses on 6 of 8
  workloads in the default configuration. Reported, not hidden.
* The `auto` algorithm heuristic is a **net loss** on the primary corpus
  (C8). Left unchanged in this experiment; fixing it is follow-up work.
* Parallel scaling is weak (≤ 2.61× on 12 threads), so "written in Zig,
  therefore ~12× faster" is **not** supported by this data.
* `zgrep -c` vs `rg -c` cannot be made byte-equal without changing `rg`'s
  binary-file semantics; the comparison was therefore run against `grep` only.

## 5. NOT_DEMONSTRATED

Explicitly out of scope or unproven by this experiment:

1. **Other platforms.** Linux x86_64 only. No Windows, macOS, or non-x86
   build has been compiled or run. The hot path uses raw `std.os.linux.*`
   syscalls, so a port is required, not a rebuild.
2. **Regex, case-insensitive, word-boundary, multiline, or `-z` matching.**
   `zgrep` implements fixed strings only. No claim is made about them.
3. **Binary files whose first match lies beyond the 8192-byte NUL probe.**
   The corpus audit found 0 such files in the corpora tested, so that path is
   exercised only by the hand-made `c.bin` (NUL at byte 6). The probe
   boundary itself (bytes 8191 vs 8192) is covered by unit tests, not by a
   cross-tool control.
4. **Correctness under concurrent mutation** of the tree while searching.
   Files are opened and read once; a file replaced mid-walk is not
   controlled for.
5. **Permission-denied and I/O-error paths at scale.** `--stats` reports
   `errors=0` on the corpora used, but no corpus with deliberate `EACCES` /
   `EIO` / broken symlinks / symlink loops was built.
6. **Memory usage and behaviour under memory pressure.** Peak RSS of the
   *test binary* is recorded (4 MB) but not of `zgrep` itself; the host had
   4.6 GB available and never swapped.
7. **Any performance claim on an isolated machine.** The host was shared
   throughout (loadavg 3.6 – 17.1). Medians of 10 interleaved runs plus an
   independent sequential pass with the same ordering are the strongest
   statement available here; absolute times will differ on a quiet host.
8. **Throughput as a hardware property.** MB/s figures use total bytes on
   disk as the denominator and include process startup; `--stats` uses text
   bytes and excludes it. Neither is a raw memory-bandwidth measurement.
9. **A claim that `zgrep` is "better than ripgrep" overall.** The data
   contradicts it in the default configuration (C6).
10. **Long-term stability / versioning.** `zgrep -V` reports `0.1.0`; no
    release process, no ABI, no guarantee of output stability across
    versions.

## 7. Follow-up (2026-11-08): commit `5c89b40` — rarest-byte SIMD, thread scratch, early exit

**Nothing above was rewritten.** Sections 1–6 describe the experiment as it was
run on the corpus of 5331 files. The corpus has since grown to **5338 regular
files / 670,595,588 bytes** (403,710,052 text bytes; 1139 files carry a NUL in
the first 8192), so absolute times below are **not** comparable with B1–B8; the
within-run ratios are. This section records what changed, what was re-verified,
and which claims from section 4 are now superseded.

### 7.1 What changed

| Change | File | Effect |
|---|---|---|
| rarest-byte heuristic + SIMD anchor | `src/search.zig` | `findMemchr` now scans for the **rarest** byte of the needle (`byte_rank` table, `rarest_offset`/`rarest_byte`) with `std.mem.findScalarPos` (vectorised), then verifies the whole needle once |
| `--algo=auto` → `.memchr` unconditionally | `src/search.zig` | Closes C8: `auto` no longer selects BMH for short needles. BMH is reachable only explicitly (`--algo=bmh`) |
| per-thread 128 KB scratch buffer | `src/main.zig`, `src/scan.zig` | small files are read straight into a reusable buffer: no `gpa.alloc`/`free`, no `lseek(SEEK_END)`+`lseek(SEEK_SET)`; files ≥ 128 KB rewind and take the mmap path |
| early exit in `-l`/`-q` | `src/scan.zig` | `scanBuffer` returns after the first match in `files`/`quiet` mode |
| single `ensureUnusedCapacity` per emitted line | `src/scan.zig` | one growth decision instead of five appends |

## 8. Kamikaze Scout & Streaming Dataflow Benchmark Suite (2026-11-08)

### 8.1 Motivation & User Proposal

In previous sessions on massive codebases, `zgrep` walked directory hierarchies
sequentially before scheduling worker threads. To eliminate this latency, the user
proposed an asynchronous hierarchical dataflow: a top-level **Kamikaze Scout**
that sweeps directory topologies with raw `getdents64`, pruning excluded directories
(`--exclude-dir`, `--no-hidden`), and streaming `DirectoryBatch` records into an
in-memory bounded ring buffer (`BatchChannel`), while worker threads grab batches
and execute rarest-byte SIMD scanning concurrently.

Implementation resides in [`src/kamikaze.zig`](../src/kamikaze.zig) and CLI flags
`-k`, `--kamikaze`, `--dataflow`, `--exclude-dir=DIR`, `--no-hidden` in
[`src/main.zig`](../src/main.zig).

### 8.4 Critical Analysis: "En Qué Fallamos Aún" (Defects, Trade-offs & Limitations)

1. **Output Non-Determinism in Streaming Mode (`-k`)**:
   Standard `zgrep` buffers slots and writes them in strict traversal order
   (byte-for-byte identical to GNU grep). In `zgrep -k`, workers stream batches
   as they finish, producing non-deterministic file output order (identical to
   ripgrep default behavior, but different from GNU grep).
2. **Gitignore / .ignore Rule Engine**:
   `ripgrep`'s primary advantage on whole repositories is automatic recursive
   `.gitignore` parsing. When scanning the entire `ISyCo` monorepo, `zgrep`
   must rely on explicit `--exclude-dir=DIR` and `--no-hidden`; otherwise it
   traverses all virtualenvs, caches, and build targets (333,978 files / 11.7 GB).
3. **Thread Creation Overhead on Tiny Corpora**:
   On small directory trees (e.g. `src/` with 8 files), GNU grep's single-threaded
   C process completes in **1.65 ms** vs **4.41 ms** for `zgrep_k` (and 4.63 ms for `rg`).
   Spawning 12 OS threads costs ~0.5ms of kernel scheduling overhead when there
   is virtually no work to distribute.
4. **Fixed-String Only**:
   `zgrep` implements high-performance literal string searching (`-F`). It does
   not contain a regex engine (NFA/DFA) for regular expressions.
5. **Single-Producer Scout Topology**:
   While workers scale across all available CPUs, the directory topology scanner
   runs as a single thread feeding the bounded ring buffer (`QueueCapacity = 512`).
   On pathological directory structures with deep nesting and few files per folder,
   the scout thread can bottleneck worker thread ingestion.

## 9. Concurrent Swarm ("Abuelo/Padres/Hijos") & Universal FilterEngine (2026-11-08)

### 9.1 Concurrent Swarm & WorkPool

To address the single-producer scout bottleneck (§8.4 item 5), `src/kamikaze.zig`
was redesigned into a unified work-stealing hybrid swarm (`WorkPool`):
* Any idle worker thread simultaneously acts as a **Directory Scout** ("Padre/Hijo")
  or a **File Scanner** ("Nieto").
* Subdirectories are enqueued onto a concurrent LIFO stack (`dir_queue`), while
  file batches are enqueued onto `batch_queue`.
* Traversal is depth-first per branch, maximizing CPU L1/L2 cache locality and
  minimizing peak memory usage.
* Termination is lock-free and deterministic via atomic in-flight counters
  (`dirs_in_flight == 0 and batches_in_flight == 0`).

### 9.2 Zero-Spawn Fast Path for Micro-Directories

To address the thread creation overhead on small trees (§8.4 item 3):
* If the search root is a single small directory ($\le 64$ files, 0 subdirectories),
  `zigrep` executes the scan entirely within the main thread with 0 thread spawns.
* Benchmark on `src/` (8 files, 20 timed runs):
  * `zigrep -k`: **1.281 ms** (min **1.018 ms**)
  * `GNU grep`: **1.543 ms**
  * `ripgrep`: **4.442 ms**
  * **Result**: `zigrep` is **1.20× faster than GNU grep** and **3.47× faster than ripgrep**
    even on tiny directories!

### 9.3 Universal FilterEngine & `.dataignore` / `.gitignore` Support

To solve the monorepo whole-tree filtering defect (§8.4 item 2), `src/filter.zig`
was implemented:
* **Built-in Noisy Defaults**: Automatically prunes `.git`, `.zig-cache`, `__pycache__`,
  `node_modules`, `.venv`, `venv`, `target`, `.cache`, `.idea`, `.vscode`, and file
  extensions `.pyc`, `.pyo`, `.o`, `.a`, `.so`, `.dylib`, `.dll`, `.class`, `.jar`,
  `.log`, `.min.js`, `.min.css`, `.map`, `.lock`, `.swp`, `.DS_Store`.
* **Native `.dataignore` and `.gitignore` parsing**: Automatically loaded from
  execution root and subdirectories.
* **CLI Chaining**:
  * `--exclude-dir=DIR1,DIR2` (comma-separated or globs)
  * `--exclude-ext=EXT1,EXT2` (e.g. `log,tmp,lock`)
  * `--include-ext=EXT1,EXT2` (e.g. `zig,rs,py`)
  * `--exclude=GLOB` / `--include=GLOB`
  * `--no-ignore`: Disables `.dataignore`, `.gitignore`, and built-in defaults for raw search.
  * `--no-default-ignore`: Disables only built-in defaults while preserving `.dataignore`.
* **Official Binary**: Installed as both `zigrep` and `zgrep` on PATH.
* **Tests**: 31/31 unit tests pass in 86 ms.
